## Finding: missing HTTP request body byte limit (high priority)

`server/nodeHttp.mjs:7` collects every incoming chunk into an array and then calls
`Buffer.concat` before invoking authentication, rate limiting or schema validation.
There is no application-level cumulative byte bound or early 413 response.
Oversized requests can therefore allocate memory before those controls run;
concurrent oversized requests increase availability risk. Field-length validation
after JSON parsing does not bound this allocation. Proxy limits were not verified
and must not be assumed to provide an application-level memory budget.

Recommended next change: impose a small explicit byte limit appropriate for the
JSON API, count actual streamed bytes (including chunked requests), reject
oversized requests before the handler, and test exact-boundary, above-boundary,
missing Content-Length, aborted upload and healthy subsequent request cases.
Bound request reading time and verify safe connection termination as well.
No fix or live traffic experiment was performed in this review.

## Follow-up fix — 2026-11-03 (local; not deployed)

- `server/nodeHttp.mjs` now caps actual streamed body bytes at 65,536, rejects an
  oversized declared Content-Length before reading, and returns HTTP 413 before
  calling the game/authentication handler. GET bodies are bounded too.
- A ten-second absolute upload deadline returns HTTP 408; trickling bytes cannot
  reset it. Node header/request timeouts are explicitly 10/15 seconds. No environment
  or hosting configuration is needed. The shorter `bodyTimeoutMs` test option is
  validated and cannot exceed the production ten-second default.
- Errors close the connection without retaining rejected chunks. A one-second
  fallback bounds remaining socket lifetime, while graceful closure lets the
  client receive the response. Abort/error paths release body buffers and timers.
- Twelve loopback HTTP tests cover ordinary requests, exact bounds with fixed and
  chunked encoding, oversized headers/chunks/UTF-8/GET, accepted/rejected Expect
  requests, incomplete and trickling uploads, aborts and subsequent healthy requests.
- Tests initially could not connect to loopback under restricted networking; the
  owner granted network permission for local testing. A trickling-upload regression
  then exposed premature connection reset; graceful-close handling fixed it.
- This mitigation bounds individual uploads, not overall concurrent connections,
  handler execution time, response sizes or public-service capacity. Trust-proxy,
  shared-IP fairness and infrastructure load gates above still remain open.
- Final verification on Node 22.23.3: **329 tests passed, 0 failed** (22 suites),
  including all twelve HTTP regressions and the six account-isolation tests.
  Frontend/server TypeScript, changed-code ESLint and Vite build succeeded. The
  existing WalletPage chunk-size warning remains non-blocking. No live deploy,
  database change or remote load test was performed.
